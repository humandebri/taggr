## ICP transfer confirmation and pending recovery — 2026-10-07

Wallet now opens an ICP transfer form and explicit confirmation showing amount, current fee, sender, canonical recipient, network and Ledger. Preparing and dispatching both validate balance/fee; confirmation expires after two minutes, rejects device-clock rollback and is bound to the signed-in owner and trust-root/Ledger network. Network scope deliberately ignores gateway/application context changes so a pending payment cannot disappear merely because a gateway changes. Transfers are signed only after the user presses Send. The request ID, original timestamp/memo and payment details are atomically saved before submission.

Pending metadata is private/no-backup, isolated by owner/network, refuses overwrite and survives sign-out. Session restoration reloads it and blocks new transfers. Record-read failures block payments without aborting unrelated session/user/safety restoration. Lookup polls the original request ID on the Ledger; confirmed success (including duplicate) or certified rejection clears that matching record. Unknown/cancelled/ambiguous outcomes retain it. No automatic resend or unknown-result discard is implemented.

Important remaining gap: a crash after metadata commit but before dispatch, or a request status that has been pruned, can leave a payment pending indefinitely. Safe explicit replay of identical deduplication arguments or independently verified transaction-history resolution must be added before calling the recovery experience complete. Actual delegated-auth transfer/recovery also remains unverified, and no mainnet payment was made.

## Explicit same-payment retry — 2026-10-07

Pending transfers now offer a separate confirmation for replay. Recipient, amount, original fee, original timestamp and memo are immutable; encoding is byte-identical to the original transfer arguments. Retry requires the same owner/trust-root/Ledger, a matching current fee, a device time within 23 hours of the original timestamp and fewer than 32 prior attempts. The current wallet is queried before constructing the mutation; low remaining balance does not prevent requesting an already-executed transaction's duplicate result. The conservative time bound leaves margin inside the documented ICP ledger transaction window. No automatic resend was added.

Each replay request ID is atomically appended before submission, retaining the original ID. Snapshot comparison prevents an old callback from clearing or extending a newer pending record. A shared process-wide lock serializes store instances so two view models cannot overwrite the pending payment. Reload preserves all IDs, including old records that lack the new optional array.

Result checks inspect recorded IDs newest first with a 45-second overall bound. Any certified successful reply/duplicate resolves the original payment; the pending record is cleared as rejected only when every recorded attempt has a confirmed rejection. An unknown/pruned request combined with a replay rejection remains pending. A replay failure retains the original record, even when that new attempt reports a known error, because it does not prove the original was unexecuted.

Verification: 33 JVM tests passed, including identical replay arguments, mixed unknown/rejected/success outcomes, distinct IDs and retry bounds. Three focused Android tests passed for durable ID append and stale snapshots, concurrent store instances, and explicit retry UI showing the original memo/recipient. Build/Lint, `make format` and `cargo check --locked` passed. Logs: `.build/android/replay-final-build.log` and `replay-device-tests.log`. The bounded emulator peaked at 4,844 MiB sampled RSS, no guard fired, and it exited with code 0. No actual delegated transfer or replay was performed; the UI callbacks and stored records in these tests were isolated fixtures.

Remaining recovery gap: records older than 23 hours, fee changes and attempts whose replies have all been pruned still need transaction-history verification. Those records cannot be discarded as successful/rejected from an unavailable status. Full authenticated payment verification, reward withdrawal, credit minting and the rest of the iOS-equivalent app scope remain unfinished.

## Running-session expiry — 2026-10-07

Android previously retained a signed-in account UI after delegation expiry even though the SDK rejected expired signatures. A single cancellable session timer now rechecks wall time at most every 30 seconds and clears the active session when idle after expiry. Activity resume and action preflight also check expiry. The timer waits for an in-flight account action to finish; it does not cancel a mutation whose outcome may already be committed. Replacing/signing out of a session cancels its timer. The API rejects access to an expired delegated identity instead of silently switching a signed operation to anonymous access.

Expiry detaches the session, cancels wallet loading, resets account-scoped UI and asks the user to sign in again. It clears stored credentials but preserves drafts/images and unresolved post/transfer/financial records. Explicit sign-out retains its existing separate draft-cleanup behavior. A late user query cannot repopulate account state after session replacement.

## Storage status and existing-bucket registration — 2026-10-07

Account now has a native Storage panel. Registered buckets can load management-canister status, controllers, module hash, memory, cycles, daily burn and an integer estimate of remaining days. Zero daily burn has no finite estimate. Metrics retain BigInteger precision instead of truncating management Nat values to UInt64. The management request addresses `aaaaa-aa` with the bucket as effective canister ID and uses the active delegated session; ordinary unauthenticated users cannot inspect controller-only status.

Existing-bucket registration is a staged part of full storage support. Preparation fetches the current account, checks the canister is running, compares its module hash with TAGGR's published storage hash and requires the signing principal among controllers. Explicit confirmation shows the bucket, owner, controllers, module, TAGGR target and network. Dispatch rechecks the account, code/controllers and two-minute quote lifetime. The backend's immutable/no-op-if-already-set bucket registration is respected; the client never treats a different registered bucket as success. Ambiguous registration errors request a current-user refresh before attempting another bucket; success is reported only after the requested bucket appears in a fresh account response.
